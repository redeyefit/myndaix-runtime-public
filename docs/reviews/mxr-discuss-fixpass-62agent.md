### [errors-drift/remote-marker-substring-not-anchored] _remote_fetch matches MXR_ markers as substrings, not line-anchored — agent text mentioning a marker misclassifies a FAILED job
- **reported** HIGH -> **calibrated** MEDIUM (real votes 2/2)
- **where:** `src/runtime/cli.py` :: _remote_fetch, lines 298 and 301 (`if "MXR_DONE_EMPTY" in stderr_text` / `if "MXR_SYNC_TIMEOUT" in stderr_text`)
- **what:** The remote path keys on the terminal markers with a bare Python substring test (`"MXR_SYNC_TIMEOUT" in stderr_text`). The established marker contract — documented in cli.py:59-65 and enforced by the phone wrapper orchestrator/phone/mxr-phone.sh:299/301/342 with `grep -q '^MXR_DONE_EMPTY$'` — is LINE-ANCHORED. On the remote side, run_job()'s _marker_safe (cli.py:547) only indents lines that START with `MXR_` (verified: `_marker_safe('...the MXR_SYNC_TIMEOUT path...')` returns the string UNCHANGED because it does not startswith). A genuinely-failed remote agent whose error text merely contains the token `MXR_SYNC_TIMEOUT` (or `MXR_DONE_EMPTY`) anywhere mid-line lands on the remote stderr, is captured into stderr_text, and the substring test fires — I demonstrated `'MXR_SYNC_TIMEOUT' in stderr_text == True` for a stderr blob whose real terminal marker on its own line was `MXR_JOB_FAILED`.
- **failure:** A remote oracle/agent job that FAILED (model 404, crash, refusal that quotes the marker name) is reported to the operator as TIMEOUT. Because the TIMEOUT branch (cli.py:339-343) then prints a recovery handle `ssh mini mxr get <id> --reply`, the operator is told a durable reply is coming for a job that failed and will never produce one — a false 'still cooking' signal that wastes a manual poll and hides the real failure. This is exactly the marker-drift class the task asked to hunt.
- **fix:** Match the markers line-anchored like the rest of the codebase: iterate `stderr_text.splitlines()` and test `line == 'MXR_DONE_EMPTY'` / `line == 'MXR_SYNC_TIMEOUT'` (mirroring the JOB_ID `startswith` loop already in _remote_fetch and the phone wrapper's `^...$` grep). This closes the false-positive AND aligns the remote consumer with the documented one-marker-per-line contract.

### [concurrency/remote-timeout-no-margin] Remote path couples local wall-clock timeout to remote sync-wait with ZERO margin, discarding successful near-budget replies as false TIMEOUTs
- **reported** HIGH -> **calibrated** LOW (real votes 2/2)
- **where:** `src/runtime/cli.py` :: _remote_fetch, lines 198 (MXR_TIMEOUT_S={timeout_s:g}) and 224-226 (asyncio.wait timeout=timeout_s)
- **what:** The remote SSH command sets MXR_TIMEOUT_S={timeout_s} (line 198) while the local asyncio.wait uses the IDENTICAL timeout=timeout_s (line 225). The remote `mxr` runs run_job, whose sync-wait loop (cli.py:458-468) waits the FULL timeout_s for the job to reach done, polling every 0.3s (line 464), THEN prints the reply and exits 0. That reply must still travel back over SSH and be drained locally. But the local asyncio.wait deadline fires at the SAME timeout_s, so when a remote job completes anywhere near the budget, the local side declares TIMEOUT and terminates the SSH proc BEFORE the just-completed reply returns. The remote's 0.3s poll granularity pushes effective completion even closer to/past the local deadline. This is the EXACT failure class the codebase's own Profile.sync_wait() guards against with _SYNC_WAIT_MARGIN_S=60 (contracts.py:39,58) — its docstring cites the 2026-07-03/06 incident where an equal local wait (180s) vs remote exec cap (900s) 'stranded its DONE reply in the ledger looking like a timeout'. The discuss remote path reintroduces that anti-pattern with zero headroom.
- **failure:** Every discuss to oracle (the only remote agent) whose job finishes near the --timeout budget returns a false '[TIMEOUT — reply may be durable: ssh mini mxr get <job_id> --reply]' even though the review succeeded. The operator must manually SSH-recover a reply that was already computed and en route. Empirically reproduced: at a 2.0s shared budget, a remote job finishing at 1.99s or 2.0s yields a false TIMEOUT with the reply lost to the terminated pipe (job finishing at 1.9s succeeds — the margin is exactly the reply-return transit time, which the code gives zero of).
- **fix:** Give the local wait a margin over the remote sync-wait, mirroring _SYNC_WAIT_MARGIN_S. Either forward MXR_TIMEOUT_S={timeout_s - margin} to the remote so the remote gives up first and the local drain has `margin` seconds to receive its reply/marker, or keep the remote at timeout_s and set the local asyncio.wait to timeout_s + margin (e.g. +30-60s) for network+flush headroom.

### [concurrency/per-agent-connection-pool] Each local participant opens its own PostgresLedger connection pool instead of sharing one
- **reported** LOW -> **calibrated** LOW (real votes 1/2)
- **where:** `src/runtime/cli.py` :: _submit_and_fetch, line 98 (led = await PostgresLedger.connect(DSN))
- **what:** Every local participant task calls PostgresLedger.connect(DSN) independently (line 98), and PostgresLedger.connect creates a fresh asyncpg pool with min_size=2, max_size=32 (postgres_store.py:108-114). A discuss with N local RESPONDER agents (currently kilabz, librarian, higgsfield are the eligible local responders) therefore opens N independent pools = N x 2 minimum connections concurrently, each torn down in its own finally (line 162). This does not serialize the fan-out (asyncpg is non-blocking, verified — the loop is NOT stalled), but it is wasteful connection churn versus opening one shared pool in _discuss_main and passing it in. - **fix:** Open ONE PostgresLedger in _discuss_main and pass it to each _submit_and_fetch (the remote path needs none), or accept an injected ledger param; close it once after the barrier. Keeps the fan-out to a single shared pool.

### [correctness/remote-fetch-no-broad-except-aborts-barrier] _remote_fetch has no broad exception guard — any unexpected error aborts the whole discuss barrier and discards every already-collected reply
- **reported** HIGH -> **calibrated** LOW (real votes 2/2)
- **where:** `src/runtime/cli.py` :: _remote_fetch (lines 189-330) vs _discuss_main (lines 377-399)
- **what:** The design's own contract (docs/mxr-discuss-design.md lines 266-268 and checklist) states: "All unhandled exceptions in _remote_fetch/_submit_and_fetch are caught and mapped to DiscussResult(error='SUBMIT_ERROR') — no exception may escape a participant task and abort the barrier." _submit_and_fetch honors this (broad `except Exception` at line 158). _remote_fetch does NOT — its only guards are `except OSError` (spawn, line 209) and `except asyncio.CancelledError` (line 254). Any other exception raised in its body (e.g. proc.terminate()/proc.kill() on an unexpected state, an asyncio edge, or a TypeError from a NaN timeout reaching asyncio primitives) propagates out of the task. In _discuss_main the collection loop `for fut in asyncio.as_completed(tasks): result = await fut` (lines 378-380) is wrapped ONLY in `except (asyncio.CancelledError, KeyboardInterrupt)` (line 381). I reproduced that a plain Exception from one participant propagates through `await fut` uncaught and the loop exits — every reply already placed in `results` is silently dropped (never printed).
- **failure:** A single remote agent (oracle) hitting any un-anticipated error path takes down the entire discuss: the other agents' successfully-collected replies are thrown away, and the process exits with an uncaught traceback (rc from asyncio.run, not the intended 0/1). The user loses the whole discussion because of one participant, which is exactly the outcome the design promised could not happen.
- **fix:** Wrap the body of _remote_fetch in a broad `try/except Exception` (preserving `except asyncio.CancelledError: raise` first) that returns DiscussResult(error='SUBMIT_ERROR: ...', ledger=host, job_id=job_id). Additionally harden _discuss_main so a raising future can never abort collection: catch Exception per-future inside the as_completed loop and record it as a failed DiscussResult, not just (CancelledError, KeyboardInterrupt).

### [correctness/nan-timeout-crash-and-passthrough] NaN/Inf timeout is not rejected — passes float() and crashes asyncio primitives (local path) / is forwarded to remote
- **reported** MEDIUM -> **calibrated** LOW (real votes 2/2)

- **what:** The discuss timeout resolution (flag None -> MXR_TIMEOUT_S -> 300.0) validates only via `float()`, which accepts 'nan' and 'inf' without raising ValueError. A NaN reaches asyncio.wait_for(..., timeout=nan) (line 125) and asyncio.sleep(nan) (line 131) in _submit_and_fetch; I reproduced that the selector rejects it with `TypeError: timeout argument must be a number or None, got float`. On the REMOTE path, NaN is also formatted into the SSH command as `MXR_TIMEOUT_S=nan` via `{timeout_s:g}` (line 198), which the remote mxr's `float()` re-accepts as NaN, and asyncio.wait(timeout=nan) at line 225 behaves nondeterministically (in my repro it returned immediately rather than waiting). ### [correctness/zero-negative-timeout-submits-then-instant-timeout] Zero/negative timeout submits the job to the ledger then immediately returns TIMEOUT without polling once
- **reported** MEDIUM -> **calibrated** LOW (real votes 2/2)
- **where:** `src/runtime/cli.py` :: _submit_and_fetch (lines 107-119)

### [correctness/submit-and-fetch-missing-newest-row-authority] _submit_and_fetch uses simpler CAS/body-selection than run_job — can display a stale/older body when the newest outbound row is leased by a real transport
- **reported** LOW -> **calibrated** LOW (real votes 1/2)
- **where:** `src/runtime/cli.py` :: _submit_and_fetch (lines 133-151) vs run_job (lines 470-538)
- **what:** run_job carries the hardened r9-r14 newest-row-authority logic: it selects `newest = next(o for o in reversed(outs) if o.get('body'))`, re-reads the DB when the newest row is not 'sent', and refuses to print an OLDER body when the authoritative newest row is leased/lost by another sender. _submit_and_fetch instead best-effort-CASes every pending row (lines 139-145) then unconditionally prints `bodies[-1]` (last truthy body, line 150) regardless of that row's ownership state. But the two code paths diverge on the exact invariant the run_job comments (r9 #3 + r10 #5) call load-bearing, and a future cli-transport sender would reintroduce the stale-answer risk here that run_job was specifically hardened against.

Latent until a cli-channel transport exists (the same latent-duplicate condition mark_outbound_sent_inline's docstring calls out).
- **fix:** Either factor the newest-row-authority logic out of run_job into a shared helper used by both, or add a short comment at _submit_and_fetch documenting the deliberate simplification and why it is safe for the discuss reply_target (no competing transport). At minimum select the newest truthy body via `reversed(outs)` rather than bodies[-1] to match run_job's ordering assumption exactly.
